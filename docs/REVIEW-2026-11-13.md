# Pre-mainnet hardening review, 2026-11-13 (branch `feat/v10-hardening`)

This pass covers:

- ConsentRegistry fixes (from the earlier `/compact-core:review-compact` on it).
- Per-contract domain tag on `owner_commitment` in all 16 contracts.
- Mainnet owner-secret rule in `scripts/owner.ts`.
- `/compact-core:review-compact` and `/compact-core:audit-compact` on TravelRuleGate, ComplianceRegistry, PsavPassport and PaymentGateway.

Clear bugs were fixed here: inconsistent state, a missing assert, a check that does nothing, or private data leaking. Design suggestions were not implemented; they are listed at the end with a recommendation.

**How the reviews ran:**

- **`review-compact`**: 10 `compact-core:reviewer` agents, one per category, each covering the 4 contracts.
- **`audit-compact`**: 1 `compact-core:security-reviewer` per contract.
- **Raw reports**: `docs/reviews/2026-11-13/`.
- **`/midnight-verify:verify`**: the plugin is not installed on this machine, so it did not run. The audit verification requests were checked against the source and, where fixed, by a regression test in the simulator.

## Deployment impact (read before merging)

`owner_commitment` changed in every contract, so existing deployments cannot be operated with this code. Their circuits check the old, untagged hash, and the new client builds proofs for the new circuits. The `accessControl` marker written by the deploy tooling moves from `owner-v1` to `owner-v2`. As a result:

- `deploy-v9.ts` treats `owner-v1` entries as not current.
- `agent.ts` and `dust-relay.ts` refuse them with "redeploy".

Preview and preprod need a redeploy after the merge. This branch performs no transaction.

## Fixed

### 1. ConsentRegistry
| Change | Test |
|---|---|
| `updateConsentPurposes` only on an ACTIVE consent (status 1). A revoked consent is no longer silently reactivated; re-consent goes through `grantConsent` (counted). | `update only on an ACTIVE consent`, `re-consent after revocation goes through grantConsent` |
| `revokeConsent` only on an ACTIVE consent: a second revoke is refused, so `total_revocations` counts real revocations. | `revoke only on an ACTIVE consent` |
| Purposes bitmask: non-zero and only the five defined bits (`<= 0x1F`) on grant and update. `policy_version > 0` on both. | `purposes bitmask: only the five defined bits, never zero` |

### 2. `owner_commitment` domain-tagged per contract (all 16)
`owner_commitment(secret) = persistentHash<Vector<3, Bytes<32>>>([pad(32, "dpo2u/owner/v1"), pad(32, "<ContractName>"), secret])`. Every `assert_owner` now calls `owner_commitment(owner_secret())`, so the check and the off-chain value come from the same circuit.

- **Difference from the brief:** the brief's single string `"dpo2u/owner/v1/<Contract>"` does not fit `pad(32, …)` for the longer names (`dpo2u/owner/v1/AgentWalletFactory` is 33 bytes). The tag is therefore split into two padded fields; the effect is the same.
- **Off-chain:** every caller already used the contract's own `pureCircuits.owner_commitment` (`scripts/owner.ts` `ownerCommit`, `deploy-v9.ts`, `registry-v9.ts`, `attest-lgpd-v9.ts`, `travel-rule-v10.ts` `checkApproverAgainstLedger`, the demos and the test helpers). No generic hash was left to replace.
- **PsavPassport sponsor:** `sp_sponsor` was the bare `persistentHash(sponsor_secret)`, which equals the old `owner_commit` of the same secret. It is now `sponsor_commitment(secret)` with its own tag.
- **Test:** `test/owner-commit.test.ts` checks that one secret gives 16 different commits, that two contracts differ, and that the sponsor commitment differs from the owner commitment.

### 3. `scripts/owner.ts`
`ownerSecret(seed, network)` never derives from the wallet seed on mainnet. It requires `DPO2U_OWNER_SECRET` and fails with a clear error, as the approver secret already did. The network defaults to `MIDNIGHT_NETWORK` and is passed explicitly by `deploy-v9.ts`, `travel-rule-v10.ts` and `paymaster-demo.ts`. Test: `test/owner-commit.test.ts` (mainnet refuses, mainnet with the env var works, testnets derive).

## Recommendations (not implemented here)

Ordered by what to settle before mainnet.

| # | Recommendation | Source | Why not here |
|---|---|---|---|
| R1 | **PsavPassport partner key.** At issuance, store a commitment to a key only the partner holds, and require it for consent. Separate the salt for partner, evidence and reviewer (today one salt opens all three). | audit H1 | Changes the issuance interface and the control-plane flow |
| R2 | **ComplianceRegistry attestation lifecycle.** `revokeAttestation` and an `attested_until`, a minimum threshold, and `hasAttestation` honouring them. Today an attestation never lapses, yet TravelRuleGate's release treats it as "current". Also bind `context` to `company_id` (the replay check never fires with a fresh nonce) and keep history instead of overwriting. | security, token, architecture, audit | New state and a change to the release semantics |
| R3 | **TravelRuleGate trust in the owner.** Registering a sanctions provider and `attestVasp` should need the approver too. `sanctions_clear` stays the owner's statement (an in-circuit non-membership proof is the follow-up). Add `unattestVasp`. | audit, security, token | Adds a second signer to operational circuits |
| R4 | **Per-institution owner secret.** Every institution gate shares one owner secret, so the `owner_commit` values are identical and linkable, and one leak compromises all of them. Derive one secret per institution, or add a deploy nonce to the constructor. | privacy, architecture | Changes deploy and institution onboarding |
| R5 | **Key rotation.** Owner and approver rotation behind both keys. `sealed` immutables (`passport`, `registry`, `self_company_id`, `threshold`) plus a redeploy runbook. | architecture, audit (all four) | Design choice: rotation vs. sealed + redeploy |
| R6 | **Reason codes.** Public reason 4 (sanctions hit) on a `transfer_id` amounts to tipping-off, and reason 2 leaks "amount >= threshold". Publish a generic FAIL and commit the detailed reason. | audit, docs | Changes the verdict format (VERDICT-FORMAT.md) |
| R7 | **Ids chosen by callers.** `proposeSponsorship` is permissionless and first-come, so it can be squatted. Derive ids in the circuit or gate proposals on a sponsor set. Add a sponsorship end path (withdraw, consent revocation). | concurrency, audit | Interface change |
| R8 | **PaymentGateway naming.** `protocol_treasury` / `total_night_deposited` are owner-asserted bookkeeping with no coin custody and a `Uint<16>` cap per call. Rename them as booked amounts, or back them with real receives. The delegation record is the owner's claim and is not tied to the holder's wallet-layer registration. | token, docs, audit | Naming / economic design |
| R9 | **Sanctions freshness.** Keep the latest `issued_at` per provider so an older, still-valid snapshot is refused. Verify a snapshot's signature once and keep a Set of verified roots, instead of a Schnorr verify per evaluation (performance). | architecture, performance | New state; performance only |
| R10 | **Commitment cost.** `labeled_commit` / `field_commit` hash twice; `persistentCommit([label, v], salt)` saves about 40% of the hashing in `issuePassport` / `consentSponsorship` (prover keys ~45 MB). | performance | Breaks the commitment format of existing data |
| R11 | **Structs and enums.** Parallel maps → struct records; status codes → enums; mark helpers `pure`; drop the redundant getter circuits. | code quality, architecture | Refactor; no behaviour change |
| R12 | **Contention on hot paths.** Evaluations are owner-serialized (one in-flight proof per gate), and `recordSponsoredAttestation` does read-modify-write on `sponsored_usage`. Use a client queue with retry, or `Map<K, Counter>`. | concurrency | Client / design |
| R13 | **Docs.** `sanctions_clear` is not tied to `list_root` (docs/TRAVEL-RULE-DISCLOSURE.md says "bound to a signed list"). The "four eyes" wording should name the in-circuit check (F2). Fix the stale "no Set type" comment in ComplianceRegistry. Check the Res. 520 vs 521 citations. | documentation | Doc pass after R3 / R6 decisions |
| R14 | **Tests to add.** Threshold boundary (`amount == threshold`, ±1), `attestVasp` / `revokeDisclosure` by a non-owner, release of an unevaluated or already released transfer, duplicate `grant_id`, PsavPassport verdict matrix and tier 3. `travel-rule-v10.test.ts` asserts that the live preview file is pre-v10, so it will fail after the redeploy (expected; update it then). | testing | Coverage beyond the fixes |
